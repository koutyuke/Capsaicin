# 雛形

## チケット

プロジェクトにチケットの雛形があれば、それを使う。なければ次の構成にする。

```markdown
# TASK-XXX 作業の名称

## 目的

何を達成するか。背景と、なぜいま必要か。

## 範囲

書いてよいファイルとディレクトリ。触らないもの。範囲外の変更が必要なら、変更せずに報告すること。

## 作るもの

番号付きで書く。参照する仕様・判断・根拠を挙げる。

## 守ること

- 禁止事項（システムの変更、git の状態の変更など）。
- 書き方の方針（短く素直に、行数の目安、標準の部品を使う など）。
- 並行して動くほかの担当と、その範囲。

## 完了条件

確かめられる形で書く（テストの有無、検証コマンドが通ること）。

## 検証

実行するコマンド。

## レビュー

PM が、指摘・対応・直したことを書く。
```

## 実装の依頼文

```text
リポジトリ <path> で、チケット <ticket> を担当してください。
最初に <AGENTS.md・チケット・関係する仕様とソース> を読んでください。

方針: <短く素直に書く／行数の目安／入れないもの>。
同じ作業ツリーで、別の担当が <範囲> を並行して変更しています。そちらには触らないでください。
git の状態を変える操作はしないでください。

報告: 変更したファイルと行数、<検証コマンド> の結果、判断に迷った点。
```

## 差し戻しの依頼文

```text
レビューの結果は <approve with fixes など> です。次を直してください。
1. <指摘>。箇所: <ファイル:行>。理由: <なぜ問題か>。直し方: <具体的に>。
2. ...
<受け入れた判断があれば、それも伝える>
報告: 検証コマンドの結果、変更したファイル、迷った点。
```

## 独立したレビューの依頼文

```text
<対象> をレビューしてください。<読むべき仕様とチケット>。
観点: 要件、単純さ、黒魔術、セキュリティ、テスト、<画面がある場合は見た目と動き>。
ファイルは変更しないでください。
報告: 判定（approve / approve with fixes / reject）、指摘ごとの重さ・箇所・根拠・直し方、実行した検証。
仕様そのものの問題は、コードの指摘と分けて書いてください。
```

PM の結論や好みの直し方は書かない。

## アドバイザーへの依頼文

```text
次の論点について、中立の立場で意見をください。
論点: <何を決めたいか>
前提と制約: <事実だけ>
選択肢: <A／B／C。PM の推奨は書かない>
返してほしいもの: 各選択肢の利点・欠点・リスク、見落としている選択肢、推奨とその理由、確かめるべき未確認の前提。
```

2系統に同じ依頼文を渡し、答えを比べてから PM が決める。
