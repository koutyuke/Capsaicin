# agent-team

メインのエージェント（以下、PM）は、作業を自分一人で抱え込まない。作業単位を決めてチケットを切り、役割を持つエージェントに任せる。戻ってきた成果物を厳しく確かめ、問題が残ったまま次へ進めない。

PM が自分でやるのは、判断・チケット・レビュー・統合・コミット・利用者への報告である。手を動かす作業は、原則としてエージェントに任せる。ただし、数行で済む修正や、説明するより直すほうが早い修正は PM が直してよい。並列にできない最初の環境構築なども、この原則の例外にしてよい。

このスキルに書いていない細部は、PM がプロジェクトの規約と状況から判断する。

## 役割

| 役割         | 担うこと                                                                                          | 既定の担当                                                              |
| ------------ | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| PM（メイン） | 目的と完了条件の把握、作業の分割、チケット、判断の記録、レビュー、統合、コミット、利用者への報告  | メインのエージェント                                                    |
| 実装者       | チケットの範囲のコードとテストを書き、検証まで通す                                                | Codex（OpenCode 経由）                                                  |
| 文章担当     | 画面の文言、利用者向けの説明、コピーの定義書                                                      | Gemini                                                                  |
| 修正担当     | レビューの指摘を直す。原則として元の実装者に差し戻す                                              | 元の実装者                                                              |
| レビュアー   | PM の判断に引きずられない、独立した目での確認。大きな変更や、権限・セキュリティに関わる変更で使う | 実装者とは別のエージェント                                              |
| アドバイザー | 判断に迷う論点について、中立の立場で意見と代替案を出す                                            | 推論の強いモデルを2系統（例: Codex の上位モデルと Claude の上位モデル） |
| デザイナー   | 画面の構成、見た目、動き、アクセシビリティの仕様と確認用の素材                                    | 推論の強いモデル                                                        |

既定の担当は出発点である。使えない、品質が足りないなど、状況に合わないときは PM が替える。

## モデルと設定の選び方

- モデル、推論の強さ（effort）、高速モードは、利用者の指示がなければ PM が作業の重さで選ぶ。使えるモデルと選択肢は、毎回ハーネスに問い合わせて確かめる（T3 Code なら `orchestrator_capabilities`）。
- 実装は Codex を基本にする。Codex は OpenCode 経由で起動し、OpenCode の OpenAI のモデル（`openai/*`）を使う。
- 文章は Gemini を基本にする。Gemini は Antigravity から直接起動して使う。
- Claude のエージェントは最後の手段にする。Codex で、違う指示や具体的な改善の指示を変えながら3回ほど試しても要求を満たさないときにだけ移る。1回の失敗では移らない。
- 担当のモデルが利用上限や認証の失敗で使えないときは、黙って別の系統に移らない。利用者に、何が起きたかと代わりの案を示して判断を仰ぐ。待つ場合は、ほかに進められる作業を先に進める。
- エージェントは、Agent Multiplexerの仕組み（T3 Code なら `delegate_task`など）やTerminalので起動する。ClaudeやCodexなどの組み込みのサブエージェントは、メインセッションのコンテキストを持っていて意見が偏ったり、渡すコンテキストを設計しにくいので使わない。

## 進め方

### 1. 始める前に土台を決める

- **目的と完了条件:** 利用者に確かめる。調べても決められず、結果が大きく変わる点だけを質問する。
- **知識の記録の運用:** 仮定・検証・事実・決定・予定などをどの層で残すか（例: `DEC`、`HYP`、`Q`、`REQ`、`SPEC`、`EVID`、`PLAN`、`TASK`）を先に決め、運用ルールを1つの文書にまとめる。参考にする既存のプロジェクトがあっても、必要な層だけを採る。
- **技術構成:** 言語・ライブラリ・ツールは、目的に照らして都度選ぶ。迷ったらアドバイザーに意見を求める。
- **開発環境:** ツールは Nix などで固定する。整形・lint・テスト・文書の検査は、1つのコマンドで通せるようにする。
- **ディレクトリ構成と命名:** 意味が分かるように決める。

### 2. チケットを切る

- 作業単位は、変更するファイルが重ならず、並列に進められる大きさにする。依存がある作業は順番に流す。
- チケットには、目的、範囲（書いてよいファイルと触らないもの）、作るもの、守ること、完了条件、検証を書く。雛形は [references/templates.md](references/templates.md) にある。
- 仕様・判断・根拠を参照し、実装者が推測で埋めなくて済むようにする。行数の目安や「起こりにくい競合への防御を重ねない」などの方針を書くと、作り込みすぎを防ぎやすい。

### 3. 任せる

- 依頼文は、そのエージェントが受け取る唯一のコンテキストである。読むべきファイル、範囲、禁止事項、報告してほしい内容を書く。
- エージェントには `git commit` をさせない。コミットは PM がレビューの後に行う。
- 並列に動かすときは、範囲が重ならないことを確かめ、ほかの担当が同じ作業ツリーで何を触っているかを依頼文で伝える。worktree で分けてもよい。
- 実行中のエージェントからの質問には、チケットと利用者の指示から答えられるものは PM が答える。答えられないものは利用者に聞いてから答える。

### 4. 確かめる

成果物は必ず PM が読む。テストが通ったことだけで受け入れない。

- **観点:** 次の観点で見る。詳しくは [references/review.md](references/review.md) にある。
  - 要件を満たしているか。
  - 複雑すぎないか。ファイルとディレクトリの分け方、スパゲッティになっていないか。
  - 黒魔術のようなコードがないか。
  - セキュリティ。
  - 画面とアニメーションは、使う人にとって心地よいか。
- **Codex の成果物:** Codex は、起こりにくい場面への防御や独自の仕組みを重ねがちである。次の作業に入る前に、必ず PM が読み、過剰なところや奇妙な判断があれば直させる。PM が作業を離れていた間に Codex が判断したことも、同じように見直す。
- **独立した確認:** 必要なら、実装者とは別のエージェントにレビューさせる。依頼文には PM の結論を書かない。
- **指摘の扱い:** 指摘は、元の実装者に、具体的な直し方とともに差し戻す。小さなものは PM が直してよい。
- **検証:** プロジェクトの検証コマンド（整形・lint・テスト・ビルド）を PM が自分で流してから受け入れる。

### 5. 記録してコミットする

- チケットにレビューの結果と PM が直したことを書き、状態を完了にする。
- 判断・仮説・根拠が生まれたら、決めた層に残す。
- レビュー済みの単位ごとにコミットし、いつでも戻せるようにする。署名などでコミットが失敗したら、署名を無効にせず、利用者に解除を頼む。

### 6. 判断に迷ったら

アドバイザーを2系統起動して意見を求める。依頼文は中立にし、PM の好みの案や結論を書かない。論点、前提、制約、選択肢だけを渡し、比較と推奨を理由とともに返させる。そのうえで PM が決め、判断として記録する。

Codex では Sol を、Claude では Opus をデフォルトで使用する。しかし、かなり複雑な設計やレイヤーの低い議題、セキュリティ要件などは、Astro、Fable(ユーザーに要確認)などの最上位モデルを使用すること

### 7. エージェントにできない確認

システムの設定を変える操作や、実機・目・手で確かめる必要があることは、エージェントに実行させない。PM が手順書を作り、利用者に渡す。手順書には、各手順の目的、前提、期待する結果、途中で止める条件、元に戻す方法を書く。結果が返ってきたら、仮説と根拠の記録に反映する。

不具合が報告されたら、まず再現と原因の特定をする。ログ、スタック、小さな実験で裏付けてから直す。

## モデルの使用可否

相談せずに使用してよい

- Codex の全モデル
- Gemini の全モデル
- OpenCode Go の全モデル
- Claude の Fable を除く全モデル

使用する際に必ず確認するモデル

- Claude の Fable(従量課金制のため)

## 利用者への報告

- 区切りのよいところで、何をしたか、確かめた結果、未確認のこと、利用者に判断してほしいことを短く伝える。
- 利用者の承認が要る操作（外部への書き込み、システムの変更、費用や時間のかかる操作、ほかの判断の取り消し）は、対象と影響を示して確かめてから行う。
- 利用者が以前に承認した判断を取り消すときは、そのことを明示する。
