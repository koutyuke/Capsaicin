# 文書の運用

この文書は、人間とエージェントが同じ規則で Capsaicin の知識を残し、引けるようにするための規則を定める。読み手が短時間で「いま何が正しいか」と「なぜそうなっているか」を把握できることを最優先にする。構造化は、ID で引くことと機械で検査することに必要な範囲に限る。

この運用を選んだ理由と、KOERU・nekomimi-maid-ramen から採用しなかったものは [`DEC-SYS-001`](meta/decisions/DEC-SYS-001-knowledge-architecture.md) にある。

## 層

知識は次の層に分ける。層ごとに答える問いが違い、同じ命題を2つの層に書かない。

| 層 | ID | 答える問い | 形式と置き場所 |
| --- | --- | --- | --- |
| 製品 | なし | 何を、誰のために、なぜ作るか | `product/*.md` |
| 要件 | `REQ-{領域}-{番号}` | 何を満たせば成立するか | `meta/requirements/{domain}.toml` |
| 仕様 | `SPEC-{領域}-{番号}` | どう振る舞うか（1件ずつ検証できる単位） | `specs/{domain}.md` の節 |
| 判断 | `DEC-{領域}-{番号}` | 何を選び、なぜ選び、何が起きたら覆すか | `meta/decisions/DEC-*.md` |
| 論点 | `Q-{領域}-{番号}` | まだ決めていないこと | `meta/questions/Q-*.md` |
| 仮説 | `HYP-{領域}-{番号}` | 正しいと仮定して進めているが、まだ確かめていない前提 | `meta/hypotheses/HYP-*.md` |
| 根拠 | `EVID-{領域}-{番号}` | 調査や実測で確かめた事実 | `meta/evidence/EVID-*.md` |
| 計画 | `PLAN-{領域}-{番号}` | 将来の機能。要件になる前のもの | `meta/plans/PLAN-*.md` |
| 作業 | `TASK-{番号}` | 誰が何をどこまでやるか（進行中のチケット） | `meta/tasks/TASK-*.md` |

パスは `docs/` からの相対パスで書いている。

### 層の使い分け

迷いやすいのは論点・仮説・根拠・判断の境目である。次の問いで決める。

- 人が選べば決まるものは**論点**にする。選択肢と帰結を並べるだけで、論点の中では決めない。決めたら判断を作り、論点は削除する。
- 確かめれば白黒がつくものは**仮説**にする。「`pmset displaysleepnow` は root なしで画面を消せる」のように、事実の主張として書く。確かめ方と、外れたときに動く要件・判断も書く。
- 確かめた結果は**根拠**にする。仮説の状態を `supported` か `refuted` に変え、根拠を指す。`refuted` なら、影響する要件・仕様・判断を同じ変更で直す。
- 根拠に基づいて選んだものは**判断**にする。判断はその時点の前提に依存するので、覆す条件を必ず書く。

確度は下げる方向にしか動かさない。推測を根拠に書かない。確かめていないことは仮説のままにする。

## 領域

| コード | 領域 | ファイル名 | 対象 |
| --- | --- | --- | --- |
| `BLK` | 抑止 | `blocking` | スリープの種類ごとの抑止、開始と解除、解除の条件 |
| `LED` | LED | `led` | Caps Lock の LED による表示 |
| `MENU` | メニューバー | `menu` | ステータスアイコンとメニュー |
| `HUD` | 画面表示 | `hud` | 切り替えたときの HUD |
| `SET` | 設定画面 | `settings` | 設定ウインドウの構成と各項目 |
| `CLI` | コマンドライン | `cli` | `capsaicin` コマンド |
| `KEY` | ホットキー | `hotkey` | グローバルホットキー |
| `HLP` | ヘルパー | `helper` | root 権限で動く処理、その導入と削除 |
| `LCY` | 起動と復旧 | `lifecycle` | ログイン時の起動、終了時の後片付け、クラッシュからの復旧、抑止の再開 |
| `UI` | 共通デザイン | `ui` | 画面をまたぐ見た目、動き、アクセシビリティ |
| `SYS` | 横断 | `system` | 対応環境、配布、言語、セキュリティ、開発環境、文書運用 |

「ファイル名」は、要件の TOML（`meta/requirements/{ファイル名}.toml`）、仕様（`specs/{ファイル名}.md`）、要件 TOML の `domain` に使う。

`SYS` は1つの領域に属さないものだけに使う。迷ったら、その知識を最初に必要とする領域に置く。

## ID と番号

- 番号は3桁で、層と領域の組ごとに振る。例: `REQ-BLK-001`、`DEC-HLP-002`。`TASK` だけは領域を持たず、`TASK-001` のように全体で振る。
- 一度使った ID は再利用しない。削除した ID の一覧も作らない。履歴は Git で引く。新しい番号は、削除したものを含めて Git の履歴にある最大の番号の次にする。例: `git log --all --format= --name-only -- docs/meta/tasks | grep -oE 'TASK-[0-9]{3}' | sort -u | tail -1`。
- 並行して作業するエージェントの採番が衝突しないよう、新しい ID はプロダクトマネージャー（PM）が割り当てる。作業の依頼に ID を含めて渡し、エージェントは受け取った ID だけを使う。
- ID は内容を直しても変えない。ファイル名も、作成後はタイトルの変更だけを理由に変えない。

## 形式

### Markdown の記録

判断・論点・仮説・根拠・計画・作業は、1件1ファイルの Markdown で、先頭に YAML Front Matter を置く。ファイル名は `{ID}-{短い英語名}.md` にする。例: `HYP-BLK-001-displaysleepnow-without-root.md`。

Front Matter の共通項目は `schema`、`id`、`title` である。`schema` はファイルの形を名乗る。名乗らないファイルや、置き場所と合わない `schema` は検査で落とす。形をディレクトリから推測すると、打ち間違えた記録が黙って検査から漏れるからである。

| `schema` | 置き場所 | 固有の項目 |
| --- | --- | --- |
| `decision` | `meta/decisions/` | `status`（`accepted` / `superseded`）、`supersedes`、`superseded_by`、`requirements`、`based_on` |
| `question` | `meta/questions/` | `requirements`、`blocks` |
| `hypothesis` | `meta/hypotheses/` | `status`（`open` / `supported` / `refuted`）、`affects`、`evidence` |
| `evidence` | `meta/evidence/` | `observed_on`、`environment`、`sources` |
| `plan` | `meta/plans/` | `depends_on` |
| `task` | `meta/tasks/` | `status`（`todo` / `in_progress` / `in_review` / `done`）、`requirements`、`depends_on`、`assignee` |
| `specification` | `specs/` | `domain`（領域のコード）。文書自体は ID を持たないので、共通項目のうち `id` を省く |

参照項目は ID の配列で書き、実在する ID だけを指す。指してよい層は次のとおりである。

| 項目 | 指してよい層 |
| --- | --- |
| `requirements` | 要件 |
| `based_on` | 根拠、仮説、判断 |
| `affects` | 要件、仕様、判断 |
| `evidence` | 根拠 |
| `blocks` | 要件、計画、作業 |
| `depends_on` | 計画なら計画、作業なら作業 |
| `supersedes`、`superseded_by` | 判断 |

根拠の `sources` だけは ID ではなく、確かめた資料の所在を書く。Web の資料は URL、リポジトリ内の資料はパス（削除した資料は、それを含むコミットとパスを `d6cb7b3:docs/requirements.md` の形で書く。`git show` で読める。コミットは `develop` の履歴にあるものに限り、マージしないブランチのコミットは指さない）、OS や SDK に入っている資料（man ページ、ヘッダー）は絶対パスで書く。例: `/usr/share/man/man1/pmset.1`、`/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/IOKit.framework/Headers/pwr_mgt/IOPMLib.h`。

実機で確かめるための試作は、マージしないブランチに置き、リポジトリには残さない。試作で得た根拠には、結果を読み解くのに要る試作の作りと操作を本文に書き、`sources` には試作を作らせたチケットを挙げる。

本文に書いた ID（`REQ-BLK-001` のような形の文字列）も、実在するものだけにする。

### 要件

1つの領域を1つの TOML にまとめ、`[[requirements]]` に1件ずつ追加する。

```toml
schema = "requirement-set"
domain = "blocking"
domain_code = "BLK"

[[requirements]]
id = "REQ-BLK-001"
title = "自動スリープを止められる"
kind = "functional"
statement = "抑止中は、利用者が操作しなくても Mac が自動でスリープしない。"
reason = "長時間の処理や放置中の作業を中断させないため。"
priority = "must"
status = "accepted"
specs = ["SPEC-BLK-001"]
depends_on = []
sources = []
```

| 項目 | 許可値 |
| --- | --- |
| `kind` | `functional`、`quality`、`constraint` |
| `priority` | `must`、`should`、`could` |
| `status` | `draft`、`accepted` |

`specs` は要件を具体化する仕様 ID の正本である。`kind` が `constraint` の要件は、振る舞いを持たないので `specs = []` でよい。それ以外の要件は、少なくとも1つの仕様を指す。`sources` には要件の出どころになった判断・根拠・仮説の ID を書く。操作の詳細、例外、受け入れ例は TOML に書かず、仕様に書く。

### 仕様

仕様は「画面」「データ」のような技術の層で分けず、領域ごとに1ファイルにまとめる。1つの振る舞いを1つの節 `## SPEC-{領域}-{番号} 名前` にし、節の先頭に `関連要件:` で要件 ID を示す。受け入れ例は、前提・操作・観測できる結果の順に番号付きの箇条書きで書く。1つの節に受け入れ例が複数あるときは、`### 受け入れ例: {何を確かめるか}` の見出しで分ける。

要件の `specs` と仕様の `関連要件` は双方向で一致させる。食い違ったら要件の `specs` を正とする。

## コードとの対応

- 本番コード（`Sources/` などのアプリ本体）に `REQ-*` と `SPEC-*` を書かない。仕様との対応はテストが持ち、テスト名に仕様 ID を含める。例: `@Test("SPEC-BLK-007 指定時刻が過ぎていれば翌日の同時刻まで抑止する")`。
- コードだけでは分からない選択の理由が判断にある場合は、コメントで `DEC-*` を引いてよい。その場でしか意味を持たない局所的な理由は、ID を作らずコメントに直接書く。

## 書き方

- 文体は常体（だ・である調）にする。
- 製品と仕様には現在の正しい状態だけを書く。検討した案、以前の挙動、編集の経緯は書かない。それらは判断の `選択肢`、Git の履歴、作業の記録が持つ。
- 製品と仕様に日付や「現時点では」のような時点表現を書かない。日付が意味を持つ根拠（`observed_on`）と作業の記録だけが日付を持つ。
- 「蓋」は書かない。ディスプレイを閉じられる Mac は「MacBook」、閉じられない Mac は「MacBook 以外の Mac」、操作は「ディスプレイを閉じる」「ディスプレイを開く」と書く。API や設定の名前（`AppleClamshellState` など）はそのまま書く。
- 画面に出る名前（設定の項目、選択肢、メニュー項目、ボタン）は、String Catalog の値をそのまま「」で書く（[`AGENTS.md`](../AGENTS.md) の「画面とコマンドの名前」）。画面の文言を変えたら、同じ変更で製品・要件・仕様・手順書・採用中の判断・未確認の仮説にある名前を直す。根拠、確かめ終えた仮説、置き換えられた判断は、書いた時点の名前のまま残す。
- 同じ規則を2か所に書かない。他の層が持つ命題は ID で参照する。
  - 悪い例: `ヘルパーは sudoers で起動する。`
  - 良い例: `ヘルパーの起動方法は DEC-HLP-001 を参照。`

## 記録の一生

### 論点を解決する

1. 判断（`DEC-*`）を作り、選んだ案・理由・覆す条件を書く。
2. 要件と仕様を、判断に合わせて現在の状態へ直す。
3. 論点への参照を外し、論点のファイルを削除する。

### 仮説を確かめる

1. 確かめた事実を根拠（`EVID-*`）に書く。環境（macOS のバージョン、機種、接続機器）と日付を必ず残す。
2. 仮説の `status` を `supported` か `refuted` にし、`evidence` に根拠を足す。
3. `refuted` なら、`affects` が指す要件・仕様・判断を同じ変更で直す。

仮説は確かめた後も削除しない。「何を前提に作り、何で確かめたか」を後から引けるようにするためである。

### 判断を変える

採用済みの判断の結論を、同じ ID のまま書き換えない。新しい判断を作り、`supersedes` で古い判断を指す。古い判断は `status: superseded` と `superseded_by` を書いて残す。結論を変えない誤字や表現の修正は、そのまま直してよい。

### 計画を要件にする

1. 計画の内容を要件と仕様に移す。
2. 必要な判断と仮説を作る。
3. 計画のファイルを削除する。

### 作業を進める

作業は PM が切る。作業には、目的、対象の要件、触ってよい範囲、完了条件、検証方法を書く。状態は `todo` → `in_progress` → `in_review` → `done` と進め、レビューで直すことが出たら `in_progress` に戻す。レビューの指摘と結論は作業の本文に残す。

`done` にする変更で、作業のファイルを削除する。終わった作業の経過は Git の履歴と PR で引く（[`DEC-SYS-018`](meta/decisions/DEC-SYS-018-delete-tasks-when-done.md)）。削除する前に、次を済ませる。

1. 作業の本文にしかない事実（調査の結果、実機での確認、レビューで分かったこと）を、根拠・仮説・判断へ移す。手順も、事実を確かめ直すのに要るものは根拠の「確かめ方」に移す。
2. ほかの文書がその作業を ID で指していたら、コミットのハッシュで指すように直す。進行中の作業の `depends_on` からは外す。

## 検査

記録を足したり直したりしたら、文書の検査を実行する。コマンドは [`AGENTS.md`](../AGENTS.md) の検証の節にある。検査が見るのは次のことである。

- `schema` の有無と、置き場所との一致
- ID の形式、重複、ファイル名と `id` の一致
- 参照項目と本文に書いた ID の実在
- 参照項目が、指してよい層の ID だけを指していること
- 要件の `specs` と仕様の `関連要件` の一致と、`constraint` 以外の要件が仕様を持つこと
- 列挙値（`kind`、`priority`、`status`）が許可値に含まれること

検査で見られないこと（内容の正しさ、現在の状態だけが書かれているか、同じ命題が2か所にないか）は、レビューで確かめる。

## テンプレート

新しく書くときは、置き場所にあるテンプレート（`*.tpl.md`、`*.tpl.toml`）を複製し、不要な節を削る。テンプレートは検査の対象外にする。
