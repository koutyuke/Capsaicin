# DEC-SYS-012 CI の検査を並列のジョブに分け、集約のジョブで合否を決める

## 結論

`DEC-SYS-011` の CI が実行する検査（`just check` と `just build`）を、次の4つのジョブに分けて並列に実行する。

| ジョブ | 実行するレシピ |
| --- | --- |
| Format and lint | `fmt-check`、`lint`、`test-scripts` |
| Package tests | `test-package` |
| App tests | `test-app` |
| Build | `build` |

- 1つが失敗しても残りは最後まで実行する（`fail-fast: false`）。
- CI の合否は、4つのジョブの結果を集める「All checks passed」のジョブだけで判断する。どれかが失敗、取り消し、スキップなら、このジョブも失敗する。集約のジョブは Ubuntu のランナーで動かす。
- リリースのワークフローは、`ci.yml` を呼び出して同じ4つのジョブを通してから、配布物を作る。

## 背景

最初の CI は、`just check` と `just build` を1つのジョブで順に実行していた。各レシピは互いの結果に依存しないので、順に実行すると、その分だけ結果が出るのが遅れる。

## 選択肢

- 1つのジョブで順に実行する。macOS のランナーは1台で済むが、所要時間は全レシピの合計になる（不採用）。
- レシピごとにジョブを分ける（6つ）。GitHub Free の macOS のジョブは同時に5つまでなので、1つが待たされる。数秒で終わる検査のためにも、Nix と Xcode の準備（1〜2分）を毎回払う（不採用）。
- 時間のかかるものを分け、速い静的検査を1つにまとめて4つにする（採用）。

## 理由

- 所要時間が、全レシピの合計ではなく、いちばん遅いジョブで決まる。
- 4つなら macOS の同時実行の上限（5つ）に収まる。
- 合否を1つのジョブにまとめると、ジョブの数や名前を変えても、合否を見る場所（バッジ、リリースの前提）が変わらない。
- リリースが CI を呼び出すので、検査の定義が `ci.yml` の1か所にまとまる。

## 影響

- macOS のランナーを4台同時に使う。公開リポジトリでは無料だが、同時に動かせる macOS のジョブの枠を使い切りやすくなる。
- ジョブを足すときは、`ci.yml` の `matrix` に足す。集約のジョブは `matrix` 全体の結果を見るので、変える必要はない。
- `docs/manual/release.md` の「そのコミットの CI が成功している」は、集約のジョブの成功を指す。

## 覆す条件

- Nix と Xcode の準備がジョブの時間の大半を占めるようになり、並列にする利点が小さくなったら、ジョブをまとめ直す。
- macOS の同時実行の上限が変わったら、ジョブの分け方を見直す。
