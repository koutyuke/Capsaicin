# DEC-BLK-006 所有を確認できない電源管理アサーションは不明のまま失敗を返す

## 結論

ネイティブ操作の結果やアサーションの所有を確定できないときは、不明状態を保ち、呼び出し元にエラーを返す。成功を装わず、重複作成や、別のアサーションの可能性がある ID の解放をしない。生存している自分のアサーションだと確認できた場合だけ、その所有を回復して操作を続ける。

これは `DEC-BLK-001` の方式を補う判断であり、置き換えではない。警告と再試行は `SPEC-BLK-007` に従う。

## 背景

調査した SDK と Apple の公開ソースでは、作成・解放の RPC が失敗しても、実際の操作結果を確定できない経路がある。プロパティの取得結果が `nil` でも、不在と読み取り失敗を区別できない。ID は同じプロセス内でも再利用されうる（`EVID-BLK-007`）。

## 選択肢

- 不明なら作り直す。既存のアサーションを重複作成し、所有を追えなくなるため不採用とする。
- 一度不明になったら、同じプロセスでは回復を認めない。自分のアサーションが残っていると確認できた場合も復旧できないため不採用とする。
- 自分が所有するアサーションの存在を確認できた場合だけ回復し、それ以外は不明を保つ（採用）。不明な ID を解放して別のアサーションに触れることも避ける。

## 理由

不在を推測して処理を進めるより、確認できた所有だけを使う方が、成功の誤報と他のアサーションへの干渉を防げるためである。

## 影響

同じプロセスでの自動回復は保証しない。不明が続く場合は Capsaicin のプロセスの再起動が必要になりうる。再起動で、権限や OS 側の障害など無関係の失敗まで直るとは保証しない。

必要なアサーションを確立できなければ、開始は `SPEC-BLK-010` に従って失敗する。警告が残っていることだけを理由に、次の開始を事前に拒否するわけではない。

## 覆す条件

操作結果と不在を確実に区別でき、ID の再利用による別のアサーションへの干渉も防げる API または手順が確認できたら、回復方法を見直す。
