# DEC-SYS-016 プレリリースにするかを、版ではなくリリース用の PR のラベルで決める

## 結論

- GitHub Release をプレリリースにするかは、版から決めない。`main` へのリリース用の PR に `S-Prerelease` のラベルがあればプレリリースにし、なければ通常のリリースにする。
- `HYP-HLP-003` を確かめるまでは、すべてのリリースに `S-Prerelease` を付ける。`0.0.x` で流れを試すときも付ける。
- `DEC-SYS-014` の「版」と `DEC-SYS-015` の「公開」にあったプレリリースの決め方は、この判断に置き換える。

## 背景

`DEC-SYS-014` と `DEC-SYS-015` では、版が 1.0.0 未満ならプレリリースにしていた。これは版の文字列による固定の規則で、1.0.0 未満でも通常のリリースとして出したい場合や、1.0.0 以上でも先行版をプレリリースとして出したい場合に対応できない。

## 選択肢

- 版が 1.0.0 未満ならプレリリースにする。版とプレリリースが結びつき、上の場合に対応できない（不採用）。
- `1.2.0-beta.1` のように、版に SemVer のプレリリースの印を入れる。`MARKETING_VERSION`（`CFBundleShortVersionString`）には数字とピリオドだけを使う慣習があり、タグと `project.yml` の版を別々に持つことになる。`just prepare-release` と PR の規則の版の照合も複雑になる（不採用）。
- PR の本文に印を書く。本文はそのままリリースノートとして公開されるので、制御のための記述が混ざる（不採用）。
- リリース用の PR のラベルで決める（採用）。

## 理由

- 版と独立して、リリースのたびに決められる。
- PR の上で見え、マージの直前まで付け外しできる。マージした時点のラベルで決まるので、本文と同じく公開の直前の判断が反映される。
- Release ワークフローの変更は、イベントのラベルを読む数行で済む。

## 影響

- ラベル `S-Prerelease` を使う。リリース用のスキル `capsaicin-release` は、PR を作る前にプレリリースにするかをオーナーに確かめる。
- 付け忘れると、意図せず通常のリリースとして公開され、公開後は変えられない。`HYP-HLP-003` を確かめる前の版を通常のリリースとして出さない守りは、版による自動の判定から、スキルの確認とオーナーの判断に移る。

## 覆す条件

- アプリ内の更新の仕組み（更新の配信の経路など）を入れ、版そのものにプレリリースの印が必要になったら、SemVer のプレリリースの印を比べ直す。
- 付け忘れによる誤った公開が起きたら、PR の規則で、`HYP-HLP-003` を確かめるまでは `S-Prerelease` を必須にするかを検討する。
