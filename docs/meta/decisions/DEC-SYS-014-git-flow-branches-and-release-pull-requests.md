# DEC-SYS-014 develop で統合し、リリース用の PR を main にマージしてリリースする

## 結論

### ブランチ

| ブランチ | 切り出し元 → マージ先 | 役割 |
| --- | --- | --- |
| `main` | — | リリースした実装だけを置く。入るのはリリース用の PR だけで、そのマージがリリースになる |
| `develop` | — | 既定のブランチ。次のリリースに向けた統合先 |
| 作業ブランチ（名前は自由） | `develop` → `develop` | 機能と、急がない修正 |
| `release/vX.Y.Z` | `develop` → `main` | 通常のリリース。`develop` のスナップショットで、人は基本的に触らない |
| `hotfix/<内容>` | `main` → `main` | リリース済みの版の緊急の修正 |

- `main`、`develop`、`release/*`、`hotfix/*` 以外の名前は自由にする。`release/*` と `hotfix/*` は、それぞれ同時に1本までにする。
- マージはすべて merge commit で行う。squash と rebase はリポジトリの設定で無効にする。
- `main` に何かが入ったら、必ず `main` を `develop` に戻しマージする。`release/*` が開いていれば、そこにも `main` をマージする。戻しマージはオーナーが `develop` に直接 push する。

### 変更を入れる先

| 変更 | 入れる先 | 出方 |
| --- | --- | --- |
| アプリ、CLI、ヘルパーの挙動に関わる変更 | 作業ブランチから `develop` への PR | 次のリリース |
| 挙動に関わらない変更（README、`docs/`、チケット、開発ツールの設定など） | `develop` に直接コミット（オーナーだけ） | 次のリリースで一緒に `main` に入る。ノートには載せない |
| リリースの準備中に見つかった、そのリリースの不具合 | その `release/*` | そのリリース。版は変えない |
| 今すぐ利用者に届けたい、リリース済みの不具合 | `hotfix/*` | すぐに PATCH を出す。同時にあるものはまとめてよい |

緊急かどうかは「版を1つ増やしてまで、今すぐ出したいか」で決め、迷ったら急がない方に入れる。

### PR とラベル

- PR のタイトルと本文の形は縛らない。種類はラベルで表す。
- `develop` への PR には、種類のラベル（`T-*`）をちょうど1つ付ける。`T-Feature`、`T-Enhancement`、`T-Bug` はリリースノートの材料にし、`T-Refactor`、`T-Test`、`T-Chore`、`T-Documentation` は材料にしない。
- 互換性のない変更には、種類に加えて `I-Breaking` を付ける。対象は、CLI の引数と出力、設定の保存形式の非互換である。ヘルパーのサブコマンドは外部から使わせないので、対象に含めない。
- リリース用の PR には `S-Release`、`hotfix/*` の PR には `S-Hotfix` と種類のラベルを付ける。
- エージェントは、チケットで指示されたときに作業ブランチを push し、`develop` への PR を作ってよい。マージはオーナーだけが行う。
- 外部からの PR は受け付ける設定のままにする。

### 版

- `project.yml` の `MARKETING_VERSION` を正とし、`CURRENT_PROJECT_VERSION` はリリースのたびに1増やす。
- どの部分を上げるかは、オーナーがリリースのたびに指定する。各部分の意味と制約は `DEC-SYS-022` に従う。
- `hotfix/*` は PATCH だけを上げる。機能や互換性のない変更を含めたくなったら、通常のリリースにする。
- 版は公開したときに初めて使われる。公開前の修正は同じ版に入れる。
- プレリリースにするかは、版によらず `DEC-SYS-016` に従う。
- 流れを試すときは、試運転用の仕組みを足さず、`0.0.x` の版で本番と同じ流れを通す。

### リリースの流れ

1. `just prepare-release <major|minor|patch>`（緊急の修正では `hotfix/*` の上で `just prepare-release patch`）が、手元だけで次を行う。前提の確認、前回のタグ以降にマージした PR とラベルの収集、版の決定、`release/vX.Y.Z` の作成、`project.yml` の更新とコミット、材料の書き出し。push と PR の作成はしない。
2. リリース用のスキルが、材料と差分から `I-Breaking` の付け忘れを探し、リリースノートを英語と日本語で書く。オーナーの承認を得てから、ブランチを push し、`main` への PR（タイトルは `Release vX.Y.Z`）を作る。
3. オーナーが、PR に配られる確認用のビルドを実機で確かめ、本文を直してマージする。
4. ワークフローが、マージした時点の PR の本文をリリースノートにして公開する（`DEC-SYS-015`）。
5. オーナーが `main` を `develop` に戻しマージする。

リリースノートは、英語の節、日本語の節、比較のリンクの順に書く。各節は、手で書く総括の後に、要対応（`I-Breaking`）、機能、修正の順で1行ずつ並べ、末尾に PR の番号を付ける。`CHANGELOG.md` は持たない。

## 背景

`DEC-SYS-010` は、オーナー1人の開発を前提に、`main` だけを共有し、PR を無効にする方針だった。運用を見直すと、次の要求が出てきた。

- `main` には、リリースした実装だけを置きたい。
- 未リリースの機能が `develop` にあっても、緊急の修正だけをすぐ出したい。
- PR を、エージェントの作業のレビューと CI の場として使いたい。PR を無効にしたかったのは、生成 AI による質の低い外部からの PR を止めたかったからで、PR そのものを使いたくないわけではない。
- PR のタイトルを縛らず、種類はラベルで決めたい。
- リリースノートを自動で用意し、英語と日本語の両方を手で直してから公開したい。
- 挙動に関わらない文書の修正は、PR なしで入れたい。

## 選択肢

- `DEC-SYS-010` のまま `main` だけで開発する。`main` に未リリースの実装が入り、緊急の修正に未リリースの機能が混ざる（不採用）。
- GitHub Flow と release-please。PR のタイトル（Conventional Commits）で版とノートが決まり、タイトルを縛ることになる。リリースノートを二か国語で書く場所もない（不採用）。
- git-flow をそのまま使う。リリースブランチで仕上げの作業をする場面がなく、ブランチを保つ手間だけが増える（不採用）。
- `develop` から `main` へ直接 PR を出す。PR を開いている間に `develop` に入った変更が、そのまま PR に乗る（不採用）。
- git-flow を基に、リリースブランチをスナップショットとして使い、緊急の修正の名前から版を外す（採用）。

## 理由

- `main` にはリリース用の PR しか入らないので、`main` が常にリリース済みの状態を表す。
- `release/*` を `develop` のスナップショットにするので、リリースの準備中も `develop` での開発を止めなくてよい。
- `release/*` は同時に1本までなので、版を名前に入れても `release/*` 同士が衝突しない。`hotfix/*` は名前に版を入れないので、版の決め直しで名前とずれない。
- 戻しマージを `main` から行うので、リリースのタグが `develop` の祖先になり、前回のタグを `git describe` で確実に見つけられる。
- 計算で決まること（版、材料）はスクリプトに置き、判断と文章（互換性の確認、二か国語のノート）はスキルに置くので、毎回同じ結果になるべき処理がぶれない。

## 影響

- リポジトリの設定を、既定のブランチ `develop`、merge commit だけのマージに変える。`main` と `develop` のルールセットは `DEC-SYS-015` に従って変える。
- `just prepare-release` が PR のラベルを読むために GitHub CLI（`gh`）を使うので、devShell に足す。
- 戻しマージを忘れると、前回のタグが `develop` から辿れなくなる。`just prepare-release` はこれを前提の確認で止める。
- 作業ブランチの push と PR の作成をエージェントに許すので、`AGENTS.md` の禁止事項を変える。
- 切り替えた時点で `main` にある、`v0.0.0` の後の未リリースのコミットは、移行前の状態として受け入れ、`develop` もそこから切る。

## 覆す条件

- 生成 AI による質の低い外部からの PR で実害が出たら、PR の作成を「Collaborators only」にする。
- 共同の開発者が加わり、オーナーだけが `develop` に直接コミットする運用が合わなくなったら、直接コミットをやめるかを見直す。
- 過去の版を並行して保守する必要が生じたら、版の系列ごとの保守ブランチを検討する。
- リリースの準備中に `release/*` で仕上げの作業をすることが増えたら、リリースブランチの位置付けを見直す。
