# DEC-SYS-018 作業は終えた変更で削除し、残す知識は根拠と判断に移す

## 結論

作業（`TASK`）は、進んでいる間だけリポジトリに置く。`done` にする変更で作業のファイルを削除し、終わった作業の経過は Git の履歴と PR で引く。作業の本文にしかない事実（調査の結果、実機での確認、レビューで分かったこと）は、削除する前に根拠・仮説・判断へ移す。終わった作業を、残す層からコミットのハッシュで指す。

## 背景

`documentation-management.md` は、リリースを切るときに `done` の作業をまとめて削除すると定めていた。`v0.0.0` と `v0.0.1` をリリースした後も、`done` の作業は78件残っていた。リリースの手順に削除の工程がなく、思い出す人がいなかったためである。

また、判断・根拠・仮説の本文が、終わった作業を ID で指していた。文書の検査は本文の ID の実在を確かめるので、作業を削除すると検査が落ちる。作業の中にしかない調査の手順や結果もあり、削除するとその知識が作業ツリーから消える状態だった。

## 選択肢

- リリース時にまとめて削除する規則を残し、リリースの手順に工程を足す。作業が終わってからリリースまでの間に、残す層から作業を指す記述が増え、まとめて直す量が大きくなる。
- 作業を Git に入れず、手元だけに置く。委譲先のエージェントは別の worktree で動くので、作業を読めない。並行するセッションから互いの作業が見えず、ID が衝突しやすい。手元のファイルには履歴もバックアップもない。
- 作業を GitHub Issues に移す。エージェントが `gh` とネットワークに依存し、文書の検査と運用を作り直す必要がある。今の規模では手間に見合わない。
- 作業を Git に入れたまま、`done` にする変更で削除する（採用）。

## 理由

- 削除が作業を終える変更の一部になるので、忘れる工程が残らない。
- 残す層が終わった作業を指していると、その削除で検査が落ちる。検査が、知識を正しい層へ移すきっかけになる。
- 委譲先の worktree からは、進行中の作業を今までどおり読める。

## 影響

- `documentation-management.md` の「作業を進める」と「ID と番号」を、この判断に合わせる。
- 作業は ID を再利用しないので、新しい番号は削除したものを含めて Git の履歴から決める。
- 進行中の作業から、削除した作業を `depends_on` で指さない。依存先が終わったら外す。

## 覆す条件

- 作業の件数が増え、終わった作業を Git の履歴から引く手間が問題になったら、Issue などの外部の管理に移すことを考える。
- 委譲先のエージェントが worktree を使わなくなったら、作業を手元だけに置くことを考える。
