# DEC-SYS-023 develop への PR に S-Preview を付けたら、署名と公証をした Debug ビルドを作り、PR のコメント1つで状態を示す

## 結論

- `develop` への PR に `S-Preview` のラベルが付いている間、ラベルを付けたときと、head に push したときに、確認用の Debug ビルドを作る。同じ PR の古い実行は取り消す。ほかのリポジトリからの PR では作らない。
- 確認用の Debug ビルドは Debug 構成のアプリで、bundle ID は `io.github.koutyuke.capsaicin.debug` である。正式版と同時に入れられ、更新の配信元と公開鍵を持たない（`SPEC-SET-007`）。
- 署名と公証は、リリース用の PR の確認用ビルドと同じ手順（`DEC-SYS-021`）で行う。その手順は、リリースと確認用の Debug ビルドが共有する1つの再利用可能なワークフローにまとめ、リポジトリを checkout しないジョブで行う。
- PR のコメントは、種類ごと（リリースの確認用ビルドと、Debug の確認用ビルド）に1つだけにし、書き換えて使う。ビルドを始めるときに「ビルド中」として作るか書き換え、終わったら「完了」か「失敗」に書き換える。完了のコメントには、ダウンロードの場所、ビルドしたコミット、構成と bundle ID、署名の状態、artifact の期限、実行のログを示す。
- コメントの文言は英語にする。

## 背景

確認用のビルドは、これまで `main` へのリリース用の PR でだけ作っていた。`develop` への PR の変更を実機で確かめるには、オーナーが手元でビルドする必要があり、手元にない Mac では確かめられなかった。Developer ID を得たので、どの Mac でも「このまま開く」を選ばずに開けるビルドを作れる。

リリースの確認用ビルドのコメントは、ビルドが終わった後に作るか書き換えていた。ビルドしている間は、コメントが古いコミットのビルドを指したままになる。

## 選択肢

構成:

- Release 構成にする。配布物と同じものを確かめられるが、bundle ID が正式版と同じなので、入れると正式版を置き換える（不採用）。
- Debug 構成にする（採用）。

作り直す契機:

- ラベルを付けたときだけ作る。ランナーの時間は減るが、push のたびにラベルを付け直す必要がある（不採用）。
- ラベルが付いている間は、push のたびに作る（採用）。

コメント:

- 実行のたびに新しいコメントを足す。同じようなコメントが並び、どれが最新か分かりにくい（不採用）。
- 古いコメントを消してから、新しいコメントを足す。通知が実行のたびに飛ぶ（不採用）。
- 1つのコメントを状態に合わせて書き換える（採用）。

## 理由

- Debug 構成なら、正式版を入れたままの Mac でも確かめられる。
- 署名と公証の手順を1つにすれば、リリースと確認用ビルドで手順がずれない。
- 1つのコメントを書き換えれば、PR を開いた人は、いまどのコミットのビルドがどの状態かを1か所で分かる。

## 影響

- macOS のランナーの時間と、Apple の公証の待ち時間が、`S-Preview` を付けた PR の push ごとにかかる。
- Debug 構成のアプリを Developer ID で署名して公証する。Debug 構成にだけ入るファイル（Xcode の debug dylib など）があれば、確認用ビルドでは作らないか、署名の対象に含める。
- `S-Preview` のラベルを GitHub に作る。PR の規則（`DEC-SYS-015`）は変えない。
- `docs/manual/release.md` のリリースの確認用ビルドのコメントの説明を、新しい形に合わせる。

## 覆す条件

- macOS のランナーの時間や公証の回数が、費用や制限の問題になったとき。
- 確認用の Debug ビルドで確かめたことが、配布物（Release 構成）と食い違う問題が起きたとき。
