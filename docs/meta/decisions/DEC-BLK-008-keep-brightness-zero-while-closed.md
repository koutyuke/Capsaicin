# DEC-BLK-008 「明るさを0」で閉じている間は、1分ごとに輝度を 0 に戻し、開けたら閉じる前の輝度に戻す

## 結論

`DEC-BLK-007` のうち、閉じている間に輝度が変えられたときの扱いを次のように改める。ほかの決定（選択肢、暗くする方式、記録、戻す場面、失敗したときの扱い、「ディスプレイを自動でオフにしない」との関係）はそのまま引き継ぐ。

- 抑止中に「明るさを0」で蓋を閉じて暗くしている間は、アプリの1分ごとの処理で内蔵ディスプレイの輝度を読み、0 より大きければ 0 に戻す。蓋が開いていると分かっているときは戻さない。
- 戻す場面（蓋が開いた通知、解除、終了、起動）では、いまの輝度によらず、記録した閉じる前の輝度を書く。閉じている間に変えられた輝度は捨てる。

## 背景

`DEC-BLK-007` では、閉じている間に利用者が変えた輝度を開けたときに上書きしないと決めていた。実機の確認で、閉じている間に外付けキーボードで明るさを上げると、閉じた蓋の中で画面が点いたままになり、開けるまで暗くならないことが分かった（`TASK-061` のレビュー）。

オーナーは、閉じている間に明るさを変えることはないので、変えた輝度を捨ててよいとした。

## 選択肢

- 何もしない。閉じている間に一度でも輝度が上がると、開けるまで光漏れ・電力・発熱を抑えられない。
- 輝度を定期的に読んで 0 に戻す（採用）。間隔は次のとおり比べた。
  - 1分ごとの既存の処理に載せる（採用）。新しいタイマーが要らない。戻るまで最大1分光る。
  - 5〜30秒の専用のタイマー。早く戻るが、閉じたら動かし、開けたら止める処理が増える。
- 輝度の変化を通知で受ける。明るさのキーの入力を拾うには追加の権限が要り、DisplayServices の変更の通知は確かめていない非公開の仕組みに頼ることになる。

## 理由

- 「明るさを0」を選んだ時点で、閉じている間は暗くしたいという意思が示されている。閉じている間は画面が見えないので、輝度が上がるのは、うっかり押した明るさのキーや、輝度を同期するほかのアプリなど、利用者の意図しない変化がほとんどである。
- オーナーは閉じている間に明るさを変えないので、戻るまでの時間を短くする利点は小さい。1分ごとの処理は抑止の解除の条件を確かめるためにすでに常に動いており、新しいタイマーも電力も増えない。
- 閉じたまま輝度 0 を書けば光が消えることは確かめてある（`EVID-BLK-012`、`EVID-BLK-013`）。
- 閉じている間の変化を捨てるので、戻すときにいまの輝度を確かめる必要がなくなり、記録した値を書くだけになる。

## 影響

- `SPEC-BLK-013` の戻す手順と受け入れ例を直し、閉じている間に 0 に戻すことを足す。`docs/manual/verification.md` の 4.7 の期待を直す。
- コントローラーは、蓋が閉じた通知と開いた通知から、いま蓋が閉じているかを覚える。戻すのに失敗して記録が残ったまま蓋が開いているときに、使っている画面を暗くしないためである。
- 明るさのキーを押してから暗くなるまで、閉じた蓋の中が最大1分光る。
- 閉じている間に利用者が意図して変えた輝度も、開けたときに閉じる前の輝度に戻る。

## 覆す条件

- 閉じたまま明るさを変える使い方があり、変えた輝度を残したいという要望が出る。
- 1分のあいだ光ることが、光漏れや発熱として問題になると分かる。
- 輝度の変化を、権限も非公開の通知も使わずに受け取れる方法が見つかる。
