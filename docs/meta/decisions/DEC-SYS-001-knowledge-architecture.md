# DEC-SYS-001 知識を製品・要件・仕様・メタ記録の層に分けて残す

## 結論

Capsaicin の知識は [`documentation-management.md`](../../documentation-management.md) の層（製品、要件、仕様、判断、論点、仮説、根拠、計画、作業）に分けて残す。KOERU の「判断は覆す条件を持つ」「記録は形を名乗る」「確度は下げる方向にしか動かない」と、nekomimi-maid-ramen の「要件は TOML、ほかは Front Matter 付き Markdown」「仕様は領域ごとの縦割り」を土台にし、仮説（`HYP`）と作業（`TASK`）の層を加える。

## 背景

Capsaicin は、私的 API や `pmset` の挙動など、試作で確かめるまで成否が分からない前提に多く依存する。仮定と事実を区別せずに書くと、確かめていない前提の上に実装が積み上がる。また、複数のエージェントが並行して実装するので、誰が何をどこまで終えたか、どの判断に従うかを、会話ではなくリポジトリから引ける必要がある。

## 選択肢

- 単一の要件定義書を育てる。読みやすいが、仮定・判断・作業が1つの文書に混ざり、どれが確かめ済みかを引けない。
- KOERU の構成をそのまま使う。FSL、予算、試験の登録簿、リリース対象などは、小さな常駐アプリには重く、保守の手間が価値を上回る。
- nekomimi-maid-ramen の構成をそのまま使う。仮説を置く層がなく、未確認の前提が論点か根拠のどちらかに紛れる。作業を記録する場所もない。
- 両者から必要な層だけを採り、仮説と作業を足す（採用）。

## 理由

- 仮説を論点と分けたのは、論点が「人が選べば決まるもの」で、仮説が「確かめれば決まるもの」だからである。混ぜると、試作で確かめるべきことを議論で決めてしまう。
- 作業を記録に残すのは、並行するエージェントへの依頼、完了条件、レビューの指摘を、会話の外で引けるようにするためである。
- 採用しなかったもの:
  - FSL による形式仕様。状態遷移が単純で、形式化の費用に見合わない。
  - 予算（`BUDGET`）と試験の登録簿（`SUITE`）。性能の上限配分や試験件数の監査が要るほどの規模ではない。
  - リリース対象（`PROFILE`）。リリースは v1 の1つだけで、範囲は要件の `priority` と計画の有無で表せる。
  - 確度タグ（`[Fact]` など）。層そのもの（根拠・仮説・論点）が確度を表すので、タグとして重ねない。

## 影響

- `docs/requirements.md` の内容を、この層に移す。移し終えたら `docs/requirements.md` は削除する。
- 文書の検査を開発環境に用意する（`documentation-management.md` の「検査」）。
- 新しい ID は PM が割り当てる。

## 覆す条件

- 記録の件数が増え、層を引くより全文検索の方が速いと分かったら、層を減らす。
- 複数のリリースを並行して保守することになったら、リリース対象（`PROFILE`）の層を加える。
