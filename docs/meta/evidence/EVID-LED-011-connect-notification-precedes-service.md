# EVID-LED-011 抑止中に接続したキーボードは、接続の通知の時点でサービスがまだ一覧になく、点灯しなかった

## 確かめた事実

`fa6cae8:docs/manual/led-fix-verification.md` の手順2-1を行った。抑止中に Lofree を接続し、10秒後に LED を目視した。2.4 GHz と Bluetooth のどちらでも、Lofree は点灯しなかった。書き込みの失敗はなかった。

Capsaicin は、`IOHIDManager` の機器の接続の通知を受けると、その場で一覧を取り直して書く。システムのログで、機器、サービス、書き込みの順を比べた。

| 接続 | 機器が現れた | キーボードのサービスの追加 | Capsaicin の書き込み | 書いた対象 |
| --- | --- | --- | --- | --- |
| 2.4 GHz | 22:22:28.054 | 22:22:28.116（`0x1000375f2`） | 22:22:28.107 と 22:22:28.124 | 2回目に `0x1000375ea` だけ |
| Bluetooth | 22:23:53.867 | 22:23:54.370（`0x1000376fc`） | 22:23:53.887 | Lofree のサービスなし |

- 2.4 GHz のレシーバーは、サービスを2つ持つ。`0x1000375ea` は primary usage が consumer control（usage page `0xc`）で、キーボードの usage にも適合する。22:22:28.109 に追加された。`0x1000375f2` は primary usage がキーボードである。
- 2.4 GHz の2回目の書き込みは、WindowServer が `0x1000375f2` の追加を記録した後だった。それでも、Capsaicin が作り直したクライアントの一覧に `0x1000375f2` はなかった。
- 抑止の前に接続した場合（手順1）は、レシーバーの2つのサービスの両方に書き、Lofree は点灯した。
- Bluetooth のサービス `0x1000376fc` は、接続の通知から約0.5秒後に追加された。その後の書き込みである解除時の `"Auto"`（22:25:17）の対象には入っていた。
- どちらの接続でも、サービスが追加された後に、書き直すきっかけはなかった。

同じ検証で、次も確かめた。

- 書き込みのたびにクライアントを作り直すと、作成後に増えたサービスが一覧に入る。2.4 GHz の `0x1000375ea` と、Bluetooth の `0x1000376fc` が、接続の後の書き込みの対象に入った。
- 抑止中にスリープして復帰した後（手順2-2、Karabiner-Elements は動作中）、書き込みの対象は復帰後の一覧と一致し、失敗はなかった。解除の HUD は通常の表示で、「一部を戻せません」は出なかった。2回行い、2回とも同じだった。
- 抑止を始めると、Capsaicin は同じ `"On"` を続けて複数回書く。内蔵だけのときは4回、Lofree（USB）と Karabiner-Elements があるときは7回で、約0.1秒の間に終わる。1回は抑止の開始による書き込みで、残りは接続の通知による書き込みである。

## 確かめ方

手順は `fa6cae8:docs/manual/led-fix-verification.md` の手順0と手順2。記録は `~/capsaicin-led-check/20261111-221214/` の `2-*` にある。機器とサービスの時刻は、`log show --info` で、登録 ID と `Service added` を含む行を絞って読んだ。

## 適用範囲

- `IOHIDManager` の機器の接続の通知が、HID のイベントシステムのサービスが一覧に入るより先に届くことの根拠に使ってよい。
- 書き込みのたびにクライアントを作り直せば、新しいサービスが見えることの根拠に使ってよい。
- 遅れの長さ（約0.06秒と約0.5秒）は、この1台での1回ずつの値である。ほかの機器での上限の根拠には使えない。

## 未確認のこと

- 通知の後、どれだけ待てばサービスが必ず一覧に入るか。
- 2.4 GHz のレシーバーで、点灯に `0x1000375f2` への書き込みだけが要るのか、両方が要るのか。
- USB で接続した場合の順序。手順2-1では試していない。
